# Workshop paper tables and figures

The workshop version of the paper (NeurIPS 2026 workshop "Transitioning from
Pre-Training to Post-Training") has eleven generated tables and five generated
figures. The camera-ready of the main paper is being built from the same
text. This page explains how this repo regenerates all sixteen, and what the
checks against the paper's own files show.

## Two evaluation protocols

- **Protocol A** is the greedy protocol with three decoding seeds (42, 1234
  and 2025). Every Phase 1 number and every number of the front-loading study
  uses it. A printed value is the mean over the three seeds, and the
  subscript is the standard deviation over those seeds. That standard
  deviation measures decoding noise of one trained model, not variation
  between training runs.
- **Protocol B** is the protocol of the OpenThoughts3-30K ("OT30K") and
  held-out-corpus experiments: one seed and sampled decoding on several
  benchmarks.

The two protocols score the same model differently, so their numbers are never
compared with each other.

## What is reproduced, and from what

| Paper file | What it shows | Source |
|---|---|---|
| `factorial_summary.tex` | Front-loading study, suite averages and language suite | Protocol A records |
| `factorial_perbenchmark.tex` | Front-loading study, every benchmark | Protocol A records |
| `phase1_zoo.tex`, `phase1_zoo_full.tex` | Phase 1 for every model | Protocol A records |
| `factorial_language.tex` | Language suite of the twelve front-loading models | Language records |
| `contrasts.tex` | Every Protocol A contrast with its bootstrap interval | Protocol A records |
| `domain_robustness.tex` | The headline contrasts under other averages | Protocol A records |
| `phase2_endpoints.tex` | OT30K endpoints | Protocol B, copied values |
| `ot3_pretrain_ablation.tex` | OpenThoughts3 removed from pre-training | Protocol B, copied values |
| `heldout_reasoning.tex`, `heldout_mv_grid.tex` | Other reasoning corpora | Protocol B, copied values |
| `factorial_main.pdf`, `frontloading_trajectory.pdf`, `phase1_zoo.pdf`, `frontloading_domains.pdf` | Figures of the above | Protocol A records |
| `phase2_receptivity.pdf` | OT30K changes and held-out corpora | Protocol B, copied values |

"Protocol A records" and "language records" are the two files listed under
Inputs. They hold one score per model, seed, benchmark and question, so every
Protocol A number above is computed here from the item scores.

"Copied values" means the numbers are typed into
`mv_post_train/data/protocol_b.py`, exactly as in the paper's generator. No
item-level records for them were released with the paper's code, so this repo
cannot recompute them. The OT30K endpoint values are the ones the earlier
analyses in this repo compare with the released LAION files (`mvpt
phase2-reconcile`). Several of those values match no released record.

Four other pieces of the workshop paper are written by hand in LaTeX and are
not generated by anyone: the pipeline diagram, the compute budget table and
the two legacy tables in `reasoning_draft.tex` and `language_draft.tex`.

## Inputs

Both files come from Ali Elganzory's artifacts repository, at a fixed commit:

```bash

mkdir -p data/workshop

curl -L -o data/workshop/ablation_frontloading_x_permissiveness_language_evaluations.csv \
  $ART/ablation_frontloading_x_permissiveness_language_evaluations.csv
```

The loader checks the records against the design before computing anything:
three seeds, eleven benchmarks with the expected number of questions each,
every model scored on every question exactly once per seed, one model per
cell, and all 36 cells of the front-loading study present. A file that fails
any of these checks stops the run.

Benchmark definitions in these records: HumanEval is the 164 Python problems.
IFEval is scored per instruction over a 500-prompt subset (769 instructions),
with the loose checker. The workshop tables keep these verdicts. The revision
scores IFEval with the strict checker, from R21 (`docs/inputs.md`).
JEEBench gives partial credit in steps of 0.25.

## Commands

```bash
# Tables to tables/workshop/, figures to figures/workshop/, and the summaries
# behind them (per-benchmark means, contrasts, domain views) to artifacts/workshop/.
mvpt render-workshop

# Compare every number in our tables with the paper's files. Exit code 1 on
# any difference. The argument is the paper's tables directory, for example a
# clone of the artifacts repository at the commit above.
mvpt check-workshop path/to/permissive-llms-artifacts/latex/tables

# Compare the Protocol A records with the earlier three-seed release
# (README input 5), question by question.
mvpt workshop-release-check
```

## Results of the checks (2026-10-06)

**Tables.** All eleven tables match the paper's files exactly, character for
character, apart from the comment on the first line. This includes all 36
bootstrap intervals and q-values, because the bootstrap uses the same random
seed, number of replicates and order of draws as the paper's generator.

**Figures.** All five figures are identical to the paper's PDFs pixel for
pixel when both are drawn at 150 dpi.

**Rounding.** Every printed mean is rounded once, from the unrounded value, to
one decimal. Every standard deviation is rounded once to two decimals. An
earlier version of the workshop tables, the iffTeX sources of 2026-10-05,
rounded some cells twice: first to two decimals, then to one. That gives the
wrong digit when the value is close to a rounding boundary. For example,
50.9477 becomes 50.95 and then 51.0, instead of 50.9. Running `check-workshop`
against those older files flags 12 means and 10 standard deviations in the
per-benchmark front-loading table, and the matching cells in the two Phase 1
tables. No suite-average mean, contrast or language value changed. No
per-benchmark mean in these records lies exactly on a rounding boundary, so
the single rounding has no ties to break.

A difference printed next to two rounded cells, such as the Delta rows of the
main table, is the difference of the printed cells, so a reader can check it
by subtracting. Contrasts are computed from unrounded scores, so they can
differ from that subtraction in the last digit. The paper's captions say so.

**Records compared with the earlier three-seed release.** The release
(`ali-elganzory/mv-posttraining-scores`, `phase1/paper-decoding-3-seeds`)
covers seven benchmarks for the Phase 1 models. Where both files have the
same model, seed and question:

| Benchmark | Models compared | Models with any difference | Questions that differ |
|---|---|---|---|
| AIME24 | 35 | 0 | 0 of 3,150 |
| AIME25 | 35 | 1 | 1 of 3,150 |
| AMC23 | 35 | 1 | 1 of 4,200 |
| LiveCodeBench | 35 | 2 | 3 of 53,655 |
| MATH500 | 35 | 6 | 65 of 52,500 |
| GPQA-Diamond | 35 | 35 | 5,425 of 20,790 |
| JEEBench | 35 | 31 | 6,936 of 54,075 |

So the paper's AIME, AMC23, LiveCodeBench and MATH500 values are the released
ones. GPQA-Diamond and JEEBench were evaluated again for the paper, and those
newer runs exist only in the Protocol A records. For example, Nemotron-CC-HQ
base GPQA-Diamond is 5.7 in the records and in the paper, and 21.0 in the
release.

**Models.** For four models, the Protocol A records and the earlier release
name different Hugging Face repositories:

| Row in the paper | Protocol A records (paper) | Earlier release |
|---|---|---|
| Nemotron-CC-HQ-16K base | `...nemotron-hq-300B-4096-longsft_16k` (created 2026-08-19) | `...nemotron-hq-300B-4096-long_sft_16k` (2026-04-29) |
| Nemotron-CC-HQ-16K SFT | `...longsft_16k-SFT-Tulu3-decontaminated` (2026-08-20) | `...long_sft_16k-SFT-Tulu3-decontaminated` (2026-05-02) |
| Nemotron-CC-HQ-16K DPO | `...longsft_16k-DPO-Tulu3-decontaminated` (2026-08-21) | `...nemotron-hq-300B-16k-DPO-Tulu3-decontaminated` (2026-04-10) |
| FineWeb-Edu-16K base | `...fineweb-edu-1.4t-300B-4096-longsft_16k` (2026-08-19) | `...fineweb-edu-1.4t-300B-4096-4096-longsft_16k` (2026-04-08) |

In each pair the two weight files differ. So these are different trained
models, not copies under a new name. On AIME, AMC23, MATH500 and
LiveCodeBench the two versions score within about 2.5 points of each other,
because all of them are close to zero there.

**Which model each row was trained from.** Every SFT model's Hugging Face card
names the model it was trained from, and so does every DPO model's. In the
Protocol A records, each SFT row was trained from the base row above it, and
each DPO row from the SFT row above it, with one exception:

- **FineWeb-Edu-16K, without front-loading.** The base row is the August
  model `...fineweb-edu-1.4t-300B-4096-longsft_16k`. The SFT row,
  `...fineweb-edu-1.4t-300B-4096-longsft_16k-SFT-Tulu3-decontaminated`, is
  from April, and its card names the April model
  `...fineweb-edu-1.4t-300B-4096-4096-longsft_16k`, which has different
  weights. No SFT or DPO model trained from the August base exists on Hugging
  Face. The likely cause is that the natural name of that SFT model was
  already taken by the April one. For Nemotron-CC-HQ-16K, whose base was also
  trained again in August, the SFT and DPO models were trained again from the
  new base. The workshop tables keep R13's August row. The revision uses the
  April model's own records since 2026-10-23 (input R20,
  [frontloading.md](frontloading.md)).

Four other rows look like exceptions but are not. Their SFT card names
another repository with identical weights: Comma0.1 (4K), MixtureVitae with
front-loading (16K), SmolLM2 (4K) and SmolLM2 (16K).
